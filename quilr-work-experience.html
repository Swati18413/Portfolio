01 · Company Overview

What is Quilr AI?

Quilr AI is an end-to-end AI security platform built around a simple but powerful idea: security should protect data, guide users, and close gaps in real time — not after the damage is done.

Most security tools are reactive — they identify threats after they have already happened. Quilr AI is different. It is proactive, using artificial intelligence to identify risks and respond to them in the moment, exactly where users are working. The platform sits at the intersection of two fast-moving forces: the rapid adoption of AI tools across organisations, and the growing complexity of data security threats that this adoption introduces.

As more teams integrate AI tools into their daily workflows, the surface area for security vulnerabilities expands dramatically. A file shared in the wrong context, a prompt that leaks sensitive information, an AI agent with access to the wrong system — these are the risks that traditional security tools were never built to catch. Quilr AI addresses this by building security that moves as fast as the people it protects: intelligent, contextual, and continuous.

The product covers the full security lifecycle — from monitoring risky user behaviours and detecting AI-related risks, to enforcing access controls, managing browser extensions, and providing visibility across an organisation's entire AI asset landscape. What makes it genuinely different is that it doesn't just alert — it explains, guides, and enables users to understand and act on security insights without needing a security engineering background.

02 · Contribution 1

AI-Powered Release Notes Generator —
built from scratch.

Every engineering team ships code. Almost none of them communicate those changes clearly to the people who need to understand them. I was given the problem. I built the solution.

The Problem I Was Solving

Before this tool existed, creating release notes at Quilr AI was entirely manual. An engineer would finish a sprint, look through dozens of commit messages — most of which were terse, technical, and written for other engineers — and try to assemble them into something coherent for a product audience. The process was slow, inconsistent, and deeply dependent on the quality of the original commit messages, which varied enormously. Notes written by one person sounded nothing like notes written by another. The structure changed every release. Non-technical audiences — customers, customer success teams, product stakeholders — frequently couldn't understand what had actually changed or why it mattered to them.

The result was that release notes were either delayed, skipped entirely, or published in a form that created more confusion than clarity. This slowed down release cycles, reduced the quality of product communication, and placed an entirely avoidable burden on developers who should have been building, not writing marketing copy about what they built.

What I Built — The System Architecture

I designed and built a RAG-based (Retrieval-Augmented Generation) AI system that automatically transforms raw GitHub commit data into structured, readable, user-friendly release notes. The system was built with a Java Spring Boot backend and integrated directly with Anthropic's Claude API for the AI generation layer. Here is how each component of the system worked, and why I made the architectural decisions I did.

Layer 1
Backend Core

Built using Java Spring Boot with Apache Maven for dependency management. I designed a set of REST APIs that handled three responsibilities: fetching raw data from GitHub, processing and filtering commit logs, and triggering the AI generation pipeline. The backend was designed as a clean, modular system where each component could be independently updated without breaking the others — a design decision that proved important when we iterated on the AI prompting strategy midway through development.

Layer 2
GitHub Integration

Integrated GitHub REST APIs to pull commits, pull request titles, descriptions, and associated metadata — author, timestamp, labels, and branch context. Crucially, I also implemented a filtering system that identified and removed low-quality or irrelevant commits before they reached the AI layer. This was important because a significant proportion of commits in any active repository are either internal refactors, test changes, or dependency updates that are meaningless to a product audience. Filtering them out significantly improved the quality of the final output.

Layer 3
RAG Pipeline

The most technically interesting part of the system. Rather than sending individual commits directly to the AI model — which would produce fragmented, low-context outputs — I built a Retrieval-Augmented Generation pipeline that grouped and structured commits before passing them to the LLM. Commits were clustered by feature, by area of the codebase, and by semantic similarity where applicable. This ensured the AI model received rich, contextually coherent input rather than isolated, disconnected messages. The difference in output quality was dramatic.

Layer 4
Claude AI Layer

Used Anthropic's Claude API for the generation layer. I designed a specific prompting strategy that defined the Claude model's role as a Product Manager writing release notes — not an engineer documenting code changes. The prompt enforced non-technical language, structured output (New Features, Improvements, Bug Fixes), and a user-impact-focused framing for every generated item. The prompt strategy went through several iterations based on output quality evaluation, and the final version consistently produced clean, readable notes that required minimal editing.

Layer 5
Output Layer

The system generated structured release notes in three clearly labelled sections — New Features, Improvements, and Bug Fixes — with consistent formatting across every release. The output was also designed to be editable by PMs after generation, so the tool served as an intelligent first draft rather than a locked output. This decision came directly from user feedback during early testing, where PMs wanted AI assistance without giving up editorial control.

Challenges I Solved Along the Way

The biggest challenge was noisy commit data. In any active codebase, a large proportion of commits are low-quality — "WIP", "fix typo", "temp", "testing" — with no meaningful information content. Sending these to an LLM produced garbage output. My solution was to build a pre-processing filtering layer that scored commits by information density and discarded those that fell below a threshold before they reached the AI layer. This single improvement had the largest impact on output quality of any change I made during development.

The second challenge was maintaining context. LLMs given isolated, single-sentence inputs produce shallow, repetitive outputs. By grouping related commits together using the RAG pipeline — clustering by feature area, by PR association, and by semantic similarity — I gave the model enough context to produce genuinely useful summaries that reflected what a release actually contained, rather than a mechanical enumeration of individual changes.

03 · Contribution 2

Supademo User Guides —
because great features deserve to be found.

Building a feature is only half the job. If users don't discover it, don't understand it, and don't adopt it — the feature might as well not exist. My second contribution at Quilr AI was solving exactly this problem.

The Problem with Feature Adoption

Quilr AI is a complex product. The security features it offers — access controls, browser extension monitoring, AI risk dashboards, decision engine configurations — are genuinely powerful, but they are also genuinely difficult for non-security professionals to navigate and understand on their own. The product team regularly shipped new features that users either didn't know existed or didn't know how to use correctly. The consequence was low feature adoption, increased dependence on the support team for basic questions, and a poor onboarding experience for new users who were encountering the product for the first time.

The traditional response to this problem is static documentation — a PDF, a help article, a written guide. The problem with static documentation in a complex product is that it requires users to context-switch: leave the product, find the document, read it, return to the product, and try to apply what they read. Many users never make this journey. They get stuck, they contact support, or they simply don't use the feature at all.

Why I Chose Supademo Over Static Docs

I made a deliberate product decision to use Supademo for user education rather than producing traditional written documentation. Supademo creates interactive, click-through product demos — guided walkthroughs that live within the product context and allow users to learn by doing rather than by reading. This choice was not accidental. I had a clear PM rationale for it: interactive demos produce significantly higher engagement and retention than static documents because they reduce the cognitive gap between instruction and action. When a user can click through a demo of exactly the workflow they need to complete, they understand it faster, remember it longer, and are more confident doing it independently.

I also made a deliberate decision to structure the demos around use cases and outcomes rather than around features. Instead of building a demo that said "Here is how the Access Controls feature works," I built demos that said "Here is how to set up access controls to prevent your team from copying sensitive data between applications." The difference is significant: one describes a feature, the other solves a user problem. Users who understand the problem their feature solves adopt it far more readily than users who only understand the mechanics of how it works.

What I Built and the Decisions Behind It

I created a series of interactive feature walkthrough demos and user guide videos covering Quilr AI's most complex and most frequently misunderstood features. Each demo was designed to be short and action-oriented — I kept individual walkthroughs under five minutes, based on the understanding that users who are trying to complete a task do not have time for a comprehensive product tour. They need the specific answer to the specific question they have right now, and they need it quickly.

Each walkthrough was structured around three elements: the problem being solved, the specific actions needed to solve it, and the expected outcome so the user knows when they have done it correctly. This structure — problem, action, outcome — mirrors the mental model users bring to any product interaction and makes the learning experience feel intuitive rather than instructional.

PM Decision
I chose interactive demos over static documentation because static docs require users to context-switch out of the product to learn. Interactive demos keep users in the product context, reduce the gap between learning and doing, and produce measurably higher engagement and feature adoption. The format choice is a product strategy decision, not just a content decision.
Impact
Improved feature discoverability and onboarding experience for new users. Reduced dependency on manual support for basic feature questions. Increased user confidence in navigating complex security workflows independently. Supported faster adoption of newly released features without requiring support team intervention for standard use cases.

Competitive Analysis —
finding the gap nobody was talking about.

I conducted a comprehensive analysis of the AI security and guardrails ecosystem — not to benchmark Quilr AI against its competitors, but to find the strategic opportunity that none of them had yet claimed.

Why This Analysis Mattered

The AI security market in 2024 was moving fast and fragmenting rapidly. New tools were appearing every month, each claiming to solve a piece of the AI governance puzzle. The challenge for Quilr AI was not a shortage of competition — it was a lack of clarity about where the most important gap in the market actually was. Without a clear view of what competitors were doing and where they were falling short, it was impossible to make confident product positioning decisions.

I was given the task of mapping the competitive landscape and identifying where Quilr AI should focus its energy. The output wasn't just a comparison table — it was a strategic recommendation that influenced the product direction of the company.

The Market Context I Uncovered

The most important finding from my analysis was not about any individual competitor — it was about a structural gap in how the entire market was thinking about AI security. As organisations increasingly adopt AI agents and multi-tool integrations, modern AI systems rely on something called the Model Context Protocol (MCP) to connect AI models with external tools and data sources. MCP is the integration layer — the point at which an AI agent reaches out to a database, a code repository, or an external API to complete a task.

This integration layer introduces a category of security risks that barely any existing tool was addressing: prompt injection attacks that exploit the tool connection, unauthorised tool execution where an AI agent takes an action it was not supposed to, and data leakage as information flows across system boundaries during agent operations. Every competitor I analysed was focused on the LLM layer — the point at which a user interacts with the AI model directly. Almost none were building security at the system level, where the agent actually does its work.

My Strategic Recommendations

Based on the analysis, I proposed three strategic directions for Quilr AI's product positioning. First, build MCP-level guardrails as a core differentiator — rather than competing on the crowded LLM guardrails layer where Lakera already has a strong position, Quilr AI should focus on the system-level security layer where no competitor has built a comprehensive solution. Second, develop real-time policy enforcement and monitoring for AI agent actions — the ability to see, in real time, what an AI agent is doing and stop it before it causes harm. Third, offer developer-friendly APIs with enterprise-grade security — bridging the gap between the enterprise-heavy complexity of Palo Alto Networks and the developer-tool simplicity of Lakera.

The strategic positioning I proposed was to frame Quilr AI as "a control layer between AI agents and external tools" — a position that no competitor had explicitly claimed and that addressed the most underserved security concern in the market. This positioning directly influenced how the product team thought about the product roadmap in the months that followed.

Key Insight from This Analysis
The most valuable competitive analysis is not the one that shows you where competitors are strong — it's the one that shows you where none of them are building. The MCP gateway layer was the biggest security gap in the AI ecosystem, and it was almost entirely unaddressed. Identifying that gap gave Quilr AI a clear, defensible product direction that didn't require competing head-to-head with well-resourced incumbents.

Product Documentation —
translating complexity into clarity.

In an AI product, the gap between what a feature does and what a user understands it to do is often enormous. Closing that gap — not with technical language, but with clear, honest, user-centred communication — was the fourth area where I contributed at Quilr AI.

Feature Research — Understanding Before Explaining

Before I could write documentation, I had to deeply understand what I was documenting. I conducted research into two of Quilr AI's most technically complex and most frequently misunderstood product areas: the Model Context Protocol (MCP) and AI Guardrails.

MCP research focused on understanding how AI models interact with external tools and systems — the tool orchestration layer, how context flows across different workflows, and what the security implications of these interactions are. Guardrails research explored the mechanisms that ensure safe and controlled AI behaviour — prompt filtering, output validation, and policy enforcement systems. Both areas were fast-moving and poorly documented in the broader technical literature at the time, which made the research work genuinely challenging and genuinely valuable.

The output of this research was not just documentation — it was a set of actionable insights for product direction and feature design. Understanding how MCP worked at a deep level made it possible to identify where the biggest risks were and therefore where the product should focus its security controls. Research and product strategy were inseparable in this context.

User-Facing "How-To" Guides

I created structured, step-by-step guides for three of Quilr AI's most commonly used features: Filters, Accounts, and the Controls Dashboard. Each guide was written with a specific philosophy: lead with the problem the user is trying to solve, not with the feature they are trying to use. A guide that starts with "The Controls Dashboard allows you to…" is less useful than one that starts with "When you need to understand which security behaviours in your organisation require immediate action, here is how to use the Controls Dashboard to find them."

Every guide included step-by-step instructions that assumed no prior knowledge of the feature, use-case driven explanations that connected each action to a real-world scenario, and clearly stated expected outcomes so users always knew when they had completed the flow correctly. The goal was to enable users to answer their own questions without opening a support ticket — and the guides were consistently referenced by the customer success team as the first resource they pointed new users toward.

Internal Product Documentation

Beyond user-facing guides, I also developed internal documentation to align the engineering, product, and customer success teams around a shared understanding of how features worked. This internal documentation covered feature functionality in plain language, expected user flows from entry point to outcome, and edge cases and non-obvious usage scenarios that the engineering team had not explicitly communicated.

Internal documentation is often undervalued in product organisations — it doesn't feel as visible as user-facing work, and its impact is harder to measure. But the alternative to good internal documentation is repeated one-on-one conversations, inconsistent product understanding across teams, and customer-facing communication that reflects different versions of the truth. Good internal documentation solves all three problems simultaneously.

Core Principle I Applied
Throughout all my documentation work, I applied a single consistent principle: explain why it matters before explaining how it works. Users who understand the value of a feature adopt it. Users who only understand the mechanics often don't. In a complex AI security product, this distinction is the difference between documentation that sits unread and documentation that actually changes how people use the product.
Impact Across All Documentation Work
Improved clarity of complex features including MCP and AI guardrails for both internal teams and end users. Reduced dependency on external support for standard feature usage. Enabled faster onboarding for new users arriving at the product without a security background. Supported smoother cross-team collaboration between engineering, product, and customer success by establishing a shared, consistent reference point for how features were supposed to work.
06 · Reflections

What I learned —
from building in a real product environment.

Shipping is the only real test

Every decision I made during the Release Notes Generator project was eventually tested by the same criterion: did the output actually work? I could have spent more time designing an elegant architecture or refining the prompt strategy in theory. But the most valuable learning came from shipping early versions, observing where the output failed, understanding why it failed, and fixing it. The filtering layer that removed noisy commits, the RAG grouping that gave the LLM proper context, the editable output that preserved PM agency — none of these came from the original design. All of them came from seeing real output fail in real ways and responding to it.

Users don't struggle with features — they struggle with understanding why features matter

The Supademo work taught me something I have carried into every product decision since: the biggest barrier to feature adoption is almost never usability. It is relevance. Users who don't understand why a feature exists for them, what problem it solves in their specific context, and what a successful outcome looks like — those users don't adopt the feature regardless of how well-designed it is. Framing every piece of user communication around the problem first changed the effectiveness of the walkthroughs dramatically.

The most valuable competitive insight is the gap, not the comparison

Most competitive analyses tell you what competitors are doing. The useful question is what they are not doing — and why. My analysis of the AI security market found a gap at the MCP gateway layer that nobody had clearly articulated. That gap became a strategic direction. The ability to look at a market, understand where every player is focusing, and then identify the empty space that none of them are building in — that is the skill I most want to carry forward as a PM.

Working at zero-to-one is uncomfortable and irreplaceable

Quilr AI was not a mature product with established processes when I joined. Features were still being defined. The market was still being understood. Documentation for complex concepts was being written for the first time. Working in that environment — where nothing is finished and everything matters — was uncomfortable in exactly the right way. It forced me to make decisions without complete information, to communicate clearly under ambiguity, and to take ownership of outcomes rather than waiting for someone else to define the path. That experience is not available at companies where everything is already figured out. I am grateful I had it early.

What this internship demonstrated
I came into Quilr AI as a PM intern and left having built a production AI system, created user education materials used by real customers, shaped competitive product strategy, and written documentation that bridged the gap between engineering and users. Every one of these contributions required different skills deployed in the same direction: understanding what users need, deciding what to build, building it, communicating it clearly, and measuring whether it worked. That is product management — and this internship is where I first did it for real.
